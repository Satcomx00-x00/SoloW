# 0021 — The commits decide the version, not the pull request

**Status:** Accepted · **Date:** 2026-09-01 · **Deciders:** Architecture
**Revises:** the versioning half of the release automation introduced with `release.yml`

## Context

`release.yml` cuts a release when a merge to main carries a version bump: it reads
`packages/cli/package.json` on the commit that just passed Verify, and if no `v<version>` tag
exists yet, it tags and ships.

That design deliberately kept the *number* out of CI. Its own words: *"Deciding the number
therefore stays where it belongs — in the pull request that earns it, while the mechanical part
(tag, npm, GitHub Release) stops being something a human has to remember at the right moment."*

The reasoning is sound and the split turned out to be in the wrong place. What a release actually
requires of a person is two things, not one:

1. decide that this change deserves a release, and of what size;
2. remember to write the number down, in the right file, in the pull request that carries the
   change.

Only (1) is judgement. (2) is bookkeeping, and it is bookkeeping with a **silent** failure mode:
forget it and the merge lands, `release.yml` finds the tag already there, and reports "nothing to
release" for a change that plainly deserved one. Nothing is red. Nobody is told. The release simply
does not happen, and is noticed later — or, more often, when someone asks why `npx` still installs
the old version.

Meanwhile (1) is already written down, on every commit in the repository. This project has used
Conventional Commits throughout, and that vocabulary — `feat`, `fix`, `perf`, `!`,
`BREAKING CHANGE:` — is a semver vocabulary. The judgement was being recorded and then thrown
away.

## Decision

**The commits since the last release decide the version. CI applies it, commits it, tags it and
ships it.**

The mapping is the conventional one:

| Commits since the last tag contain | Result |
| --- | --- |
| a `!` marker or a `BREAKING CHANGE:` / `BREAKING-CHANGE:` footer | major |
| a `feat` | minor |
| a `fix` or a `perf` | patch |
| only `chore`, `docs`, `test`, `refactor`, `style`, `build`, `ci` | **no release** |

The largest wins, not the last. Merge commits are excluded — a merge subject is generated by git
and describes no change of its own.

**Below 1.0.0, a breaking change moves the minor rather than the major.** 0.4.1 with a `feat!`
becomes 0.5.0, never 1.0.0. Both semantic-release and changesets default to this, and the reason is
worth stating: 1.0.0 is not a fact about a diff. It is a declaration that the interface is stable
and that breaking it will henceforth cost a major. No commit message can make that promise on a
maintainer's behalf. Reaching 1.0.0 stays a deliberate hand edit to `packages/cli/package.json`.

**The reading lives in `packages/cli/scripts/next-version.ts`, under test, not in the workflow's
shell.** This is the one part of a release that can be wrong *without failing*: a bad rule does not
error, it publishes 0.4.2 where 0.5.0 was meant, and npm records that permanently. `publish.yml`'s
guard cannot catch it — that guard compares the tag against the manifest, and they agree either
way. Shell embedded in YAML cannot be unit-tested; a module can, and is.

Two properties the job needs now that it **commits** where it previously only tagged:

- **It stands down if main has moved past the tree Verify passed.** Those intervening commits have
  not been through Verify, and committing on top of them would release them. Nothing is lost:
  whatever landed in between had its own push, its own Verify run and its own Release run, and that
  run sees a matching tip. The release is deferred by one merge, never dropped.
- **The branch and the tag are pushed with `--atomic`.** Without it a rejected branch push can
  still leave the tag pushed, naming a commit no branch contains — and Publish would then be
  dispatched at it. Verified by experiment, not assumed: the same rejected push leaks the tag
  without `--atomic` and does not with it.

The recursion ends by construction rather than by `[skip ci]`: the commit CI pushes is a
`chore(release)`, and the tag points at that very commit, so the Verify run it triggers finds an
empty range and cuts nothing. Main's tip stays verified, which `[skip ci]` would have cost.

## Considered options

- **Commits decide, CI commits the bump (chosen).** The judgement stays with the author, expressed
  in the vocabulary they already write. The bookkeeping stops being a thing to remember. The cost
  is that CI now writes to main, and that a mis-typed commit type changes a release.

- **Keep the manual bump, and fail the merge when it is missing.** A required check that refuses a
  PR whose commits imply a release but whose manifest is unchanged. Rejected as the worst of both:
  it keeps the bookkeeping *and* adds a gate that blocks documentation-only changes unless it
  reimplements this decision's classification anyway — at which point the classification exists and
  may as well apply itself.

- **A release-please / changesets bot.** A well-trodden path, and it adds a dependency, a bot
  identity, a permanent open pull request, and a second source of truth for the version. The rule
  set that actually applies here fits in one tested file with no dependencies. Worth revisiting if
  this ever needs changelog generation per package — today `gh release --generate-notes` covers it.

- **Tag every merge to main.** No judgement required at all, and rejected: it publishes a version
  for a typo fix in a comment, and makes the version number meaningless as a signal.

## Consequences

- Positive: a release cannot be silently forgotten. The commits that deserve one produce one.
- Positive: the version number becomes a *derived* fact, so it can no longer disagree with the
  history it claims to describe.
- Positive: the classification is testable, and tested, including the 0.x rule and both footer
  spellings — where before the equivalent judgement existed only in a person's memory.
- Negative: **a mis-typed commit type now has a consequence.** Writing `chore:` for a bug fix
  releases nothing; writing `feat:` for a rename cuts a minor. The convention was previously
  cosmetic and is now load-bearing, which is worth saying out loud to contributors.
- Negative: **CI writes to main.** It needs `contents: write` and an unprotected branch, or a rule
  that admits the release bot. That is a real widening of what the workflow can do, mitigated by
  the tip check and the atomic push but not eliminated by them.
- Negative: every release costs one extra Verify run, on the `chore(release)` commit. Deliberate —
  the alternative, `[skip ci]`, leaves main's tip unverified.
- Negative: a squash-merged pull request collapses to one commit, so the *body* of that commit is
  where a `BREAKING CHANGE:` footer has to live. A break declared only in the description of a PR
  that is squashed will not be read.

## Out of scope

- **A CHANGELOG.md.** `publish.yml` already creates the GitHub Release with `--generate-notes`,
  which writes from the commits and pull requests since the previous tag — the same history this
  decision reads. A second, hand-maintained rendering of it would drift.
- **Per-package versions.** `packages/cli` is the only published artifact; the other workspaces
  carry a version that nothing reads.
- **Prereleases.** `next-version.ts` throws on a version carrying a `-rc.1` or build suffix rather
  than guessing at it. Adding a prerelease channel is a decision of its own.
